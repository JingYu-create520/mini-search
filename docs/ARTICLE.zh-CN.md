# 我从零写了一个能搜中文的搜索引擎，主代码 6005 行，零依赖

用法就一行：

```bash
java -jar mini-search.jar          # http://localhost:9200
```

里面装了一份 84 篇文档的演示语料，断网也能搜。没有 Lucene、没有 HanLP、没有 Spring、没有向量数据库，也不用下载任何模型。主代码 6005 行、38 个文件，jar 213 KB。仓库在 [github.com/JingYu-create520/mini-search](https://github.com/JingYu-create520/mini-search)。

先说清楚为什么自己写。中文检索的教学项目大多停在"能跑"，工业引擎又重到没人读完。中间那块是空的：一个能当场演示、又能一层层讲明白的东西。只要引入 Lucene，"每层都能读懂"这句话就作废了，所以连 JSON 解析都是我写的。

另一个原因是我想搞清楚"这次改动到底变好了没有"这件事。所以下面每一个数字都是 `mini-search eval` / `mini-search bench` 跑出来的，两条命令任何人都能复现。

先放结果，38 条手工标注的查询，看前 5 条：

| 模式 | recall@5 | nDCG@5 | top5 有命中 |
|---|---|---|---|
| bm25 | 0.934 | 0.912 | 36/38 |
| hybrid（RRF 融合） | 0.934 | 0.916 | 36/38 |
| vector（本地 bge 模型） | 0.987 | 0.957 | 38/38 |

5 万篇文档的规模测试：倒排索引 13.6 秒建完，BM25 查询 p50 10.3 毫秒、p95 35.2 毫秒。

下面讲四件我被现实教育过的事。

## 分词：词典不重要，能自己长词才重要

内置词典我最后只留了大约 1900 条通用词。手写词典永远追不上领域词汇，而一个教学项目里塞八万条词条，只会让人更不敢读它。

这里我中途改过一次主意。最初的设计文档里写的是用 HanLP 分词，理由很正当：它是纯 Java、许可干净、效果比手写的强。我甚至把"最新坐标与许可"列成了开工第一天要验证的事项。真开始写分词器的那天早上，我把它划掉了——不是我写不过它，是我一旦引入，这个项目就没有讲的东西了：读者看完倒排索引和 BM25，遇到"词是怎么切出来的"只能翻另一个仓库。这个决定让分词部分多写了六百多行（`analyzer/` 683 行，全是本该由 HanLP 干的事），值不值你自己判断，但至少"为什么不用 HanLP"这个问题我现在能答。

真正干活的是统计新词发现。对语料里所有字符 n-gram 算三个数：出现得够不够多；把它从中间任何位置切开、两半各自出现的概率能不能解释整体出现的概率（凝固度）；它左右能接多少种不同的字（自由度，两边取更受约束的那个）。三个都过关才承认这是个词。

第一个坑就埋在这里。我一开始用原始 PMI 当凝固度，阈值定 3.0，结果 84 篇文档只挖出 75 个词，"螺旋钻机"这种明摆着的新词直接被毙。问题不在算法，在数值：PMI 公式里带一项 `log(corpus_total)`，语料从七千 token 涨到七百万 token，同一个阈值一边能过一边不能过。也就是说这个阈值根本没有意义。

换成 NPMI 就好了，它把 PMI 除以这个词自身的信息量，值域固定在 [-1, 1]，跟语料大小无关。

```java
double pw = (double) fg / c.total;
double selfInfo = -Math.log(pw) / Math.log(2);
for (int i = 1; i < g.length(); i++) {
    double fl = Math.max(counts.get(left),  0.5);
    double fr = Math.max(counts.get(right), 0.5);
    double pmi = Math.log((double) fg * c.total / (fl * fr)) / Math.log(2);
    best = Math.min(best, pmi / selfInfo);
}
```

取 min 不取平均，是因为一个串只要存在一种"切开之后两半各自都很常见、合起来也不奇怪"的切法，它就不像词。

还有个方向容易搞反：如果某个候选的一半从来没单独出现过，直觉是"证据不足，毙掉"。恰恰相反，两半都不单独出现的串才是最像新词的。所以这里给两半的计数加了 0.5 的平滑，而不是判零分。

分词的质量靠一份 golden master 锁着：`src/test/resources/analyzer-gold.txt`，62 条中英混排句子和它们的期望切分。改分词必须重新生成这个文件并看 diff，`AnalyzerTest` 对任何不一致直接报错。

## BM25：我把字段数当成了文档数

IDF 的分母应该是包含这个词的文档数。我有标题、正文、标签三个字段、三份倒排，当时写成了这样：

```java
// 看起来很有道理，其实是错的
for (int f = 0; f < FIELDS.size(); f++) if (postings[f].containsKey(term)) n++;
return n;                      // 返回的是 1 或者 2
```

结果所有词的 IDF 都挤在 ln(1+(84-1.5)/1.5) 附近，罕见词和常见词一样响，BM25 实际上退化成了"谁词频高谁赢"。查出来的结果依然看着挺合理，这就是最难发现的那类 bug。

抓它的是条单测，写的是"df=1 的词必须比 df=2 的词响"：

```java
double byRare   = bm25.score(idx, List.of("疫苗")).get(0);
double byCommon = bm25.score(idx, List.of("资料")).get(1);
assertTrue(byRare > byCommon);
```

修完 recall@5 从 0.921 到 0.934。0.013 听着不多，但如果没有这条测试，我会带着这个 bug 一直往下做，后面所有对比数字都是脏的。

顺带说下三个旋钮。k1 管同一个词出现十次比出现三次强多少（饱和），b 管长文档惩罚多少，IDF 让罕见词说话更响。标题、正文、标签各自加权 3/1/2，所以标题命中一次能盖过正文命中一次，而它们共用一份索引。

## 向量：84 篇文档训不出任何东西

原本的计划里有"本地跑 bge 小模型"。做到这一步我发现真正的问题不是模型多大，而是我手上只有 84 篇文档。

我先用手写的 SGNS（skip-gram 加负采样）在同一份语料上训了词向量，然后老老实实跑评测：

```
| mode    | recall@5 | nDCG@5 |
| bm25    | 0.934    | 0.912  |
| vector  | 0.026    | 0.011  |   约等于随机
| hybrid  | 0.671    | 0.434  |   被这一路拖垮
```

原因不神秘：SGNS 要几百万 token 的上下文才收敛，这份语料一共七千 token。训不出语义，只训出噪声。而 RRF 是很诚实的，它会把噪声一起融进来，于是混合比纯 BM25 更差。

同一套代码在 5 万篇文档（约七百万 token）上就正常了：30000 词表、5100 万次梯度更新、训练 140 秒、HNSW 建图 156 秒、hybrid p50 21.6 毫秒。

所以我做了两件事。

给向量层加了数据量门槛，低于 40 万 token 就不启用，启动时把原因打印出来：

```
[mini-search] vector layer skipped: 7,048 corpus tokens < 400,000 needed for a useful embedding
```

宁可少一路召回，也不要让一路噪声去污染排名。想强开有 `--force-vectors`，但我会在 README 里告诉你那样做的实测后果。

小语料的语义改用更老的办法：分布式同源词典。对每个词统计"出现在同一篇文档里的其他词"，用二值文档向量的余弦排序，查询时把 top-k 邻居拼进查询再跑 BM25。这是 SMART 那代的东西，1970 年代就在用，不需要训练，84 篇文档也能挖出 1220 个词条，而且真的能把"纸币"接到"纸质货币"。

## 后来还是把 bge 接上了

上面这套门槛加词典，是在"没有预训练模型"的前提下能做到的最好。但门槛本身不解决同义词问题。有两条查询我试了所有办法都打不中：

- "小孩高烧不退是细菌感染吗"，目标是《感冒和流感的区别》
- "为什么海边城市冬天不太冷"，目标是《海洋如何调节气候》

前者考的是"高烧不退"和"流感症状"之间的常识，后者考的是"海边城市冬天不冷"和"比热容"之间的物理知识。这种东西不在语料里，只能来自模型。

于是加了 `scripts/fetch-model.sh`，从 hf-mirror 拉 bge-small-zh-v1.5 的 int8 ONNX（24 MB）和 ONNX Runtime（93 MB），`--model` 一个参数换掉编码器，门槛自动失效。实测 recall@5 0.934 涨到 0.987，那两条全回来了。

它不是默认，也不进 jar：ONNX Runtime 在 pom 里是 `provided`，权重不进 git。想要最强语义就多写一段 `-cp`，这个取舍留给用的人自己决定。

这里又踩了两个坑，都跟"错了也看不出来"有关。

一个是融合权重。我一开始把三路等权融合，hybrid 只有 0.927，比纯向量的 0.957 低一大截——两条弱词法列表在拖后腿。扫过 `--fusion` 之后定在 1 / 0.5 / 6 才追上向量本身。"混合一定比单路好"是个迷信。

另一个是池化和指令前缀。BGE 用 CLS 池化，你换成 mean 也照样跑、向量照样"看起来对"，只是排序悄悄变差；中文 BGE 训练时只在查询侧加了 `为这个句子生成表示以用于检索文章：` 这个前缀，加到文档上或者两边都不加都会掉召回。所以这两个都做成了开关（`--pool`、`--no-instruct`），默认取实测更好的那边。

## HNSW：难的不是图，是怎么知道它没写错

多层可导航小世界图全手写：节点层级按几何分布抽样，插入时逐层贪心逼近，在目标层用 `efConstruction` 宽度的候选队列扩展，双向连边，超容量按距离裁剪。

图本身几百行，真正让它能用的是测试。生成 1500 条随机向量，跟暴力 KNN 逐条查询比对，recall@10 必须 ≥ 0.95；再加一条"ef 调小，召回不允许变好"。第二条看着像废话，其实专门用来抓那种把队列上限写错、结果看起来"又快又准"的情况。

裁剪我用的是"按距离取最近 M 个"，比论文里的相对近邻启发式简单，在聚簇数据上会亏一点召回。亏多少是测出来的，所以它是一个已知的取舍，不是一个隐藏的问题。

## 爬虫：讲礼貌是功能的一部分

robots 规则按最长前缀优先，`Allow` 能盖过 `Disallow`；每个域名独立限速，支持 `Crawl-delay`；URL 先归一化（去 fragment、参数排序、主机小写、默认端口折叠）再做 64 位指纹去重；编码按 BOM、响应头、meta 声明、UTF-8 严格试解码、GBK 的顺序判。

测试对着本地 HTTP 服务器跑，不碰外网：404、500、robots 禁爬、无正文页、GBK 页、限速间隔，每一项都有断言。所有失败都变成 `CrawlResult{ok:false, reason:...}`，不抛异常。

正文抽取用链接密度：块级标签切成行，行内链接文字单独计数，链接占比过半或者短于 12 字的行丢掉，剩下的取连续段里非链接字符最多的一段。它不完美，一段被链接海洋包围的短正文可能输给壳子，但"抓不到正文就只索引标题、且不崩"是保证并且测了的。

## 没做的和做不到的

不做分布式、faceted 聚合、拼写纠错、学习排序、多语言分析器、权限系统。索引落盘目前是单段快照，没有后台归并——5 万文档下归并买不到任何东西。

有件事我特意留着没说漂亮：那两条同义词查询在零依赖那条路上仍然打不中，只有装上模型才行。Docker 我在这台机器上真跑了，构建 425 MB 镜像、`compose up` 之后接口正常。同源词典在合成语料上会退化，因为 5 万篇 bench 文档是拿同一批句子重组的，几乎所有词互相共现，余弦失去区分度，那次只挖出 6 个词条——真实文档天然是稀疏的，所以这不算 bug，但确实是个边界。

代码按这个顺序读，每层都不到 800 行：

```
analyzer/  683  归一化、双向最大匹配、统计新词挖掘
index/     479  term -> (docs + positions)、变长编码、删除位图
ranking/    82  BM25
semantic/  145  分布式同源词典
vector/   1054  SGNS 词向量、暴力 KNN、HNSW、WordPiece、可选 ONNX
hybrid/     76  RRF
search/    413  查询编排（一条查询的完整路径就这一个文件）
crawl/     726  礼貌爬虫与正文抽取
```

```bash
git clone https://github.com/JingYu-create520/mini-search
cd mini-search && mvn -B package
java -jar target/mini-search.jar eval
```

如果只看一个东西，建议看 `data/eval/report.md`。它把每条查询、每种模式的命中和未命中都摊开了。检索系统这点尊严，只能靠这张表撑着。
