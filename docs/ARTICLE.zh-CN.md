# 我从零写了一个能搜中文的搜索引擎，主代码 5573 行，零依赖

> 一句话：`java -jar mini-search.jar` → 浏览器打开 localhost:9200，就能搜中文。中间没有 Lucene、没有 HanLP、没有 Spring、没有向量数据库，也没有任何要下载的模型。
>
> 代码：https://github.com/JingYu-create520/mini-search

写这篇的动机不是"我会实现倒排索引"，而是这个项目里**有四个决定是被实测数据逼出来的**，我觉得这四个决定比代码本身更值得讲。

先把结论摆出来，全部可以在仓库里复现（`mini-search eval` / `mini-search bench`）：

| 指标 | 数值 |
|---|---|
| 38 条人工标注查询，bm25 recall@5 | 0.934 |
| hybrid nDCG@5 vs bm25 nDCG@5 | 0.918 vs 0.912 |
| 5 万文档倒排构建 | 13.6 秒 |
| 5 万文档 BM25 查询 | p50 10.3 ms / p95 35.2 ms |
| HNSW 对比暴力 KNN，recall@10 | ≥ 0.95（测试锁死） |
| 主代码 / 运行时依赖 / jar 体积 | 5573 行 / 0 个 / 205 KB |

## 一、中文分词：词典不重要，"从语料里长词"才重要

内置词典我最后只留了约 1900 条通用词。理由很简单：手写词典永远追不上领域词汇，而一个教学项目里塞进 8 万条词条，只会让人更不敢读它。

真正干活的是统计新词发现。对语料里所有字符 n-gram 算三个数：

- **频次**：出现得够不够多；
- **凝固度**：把它从中间任何位置切开，两半独立出现的概率能不能解释整体出现的概率；
- **自由度**：它左边和右边分别能接多少种不同的字（信息熵），取更受约束的那一边。

三个都过关，才承认"这是一个词"。

这里我踩了第一个坑，而且是很典型的那个：**一开始用原始 PMI 当凝固度，阈值定 3.0。** 结果在小语料上什么都挖不出来——84 篇文档时只挖出 75 个词，"螺旋钻机"这种标准答案直接被毙。原因不是算法错，是**原始 PMI 的数值会随语料规模漂移**，因为公式里有个 `log(corpus_total)` 项。语料从 7 千 token 涨到 700 万 token，同一个阈值一个能过一个不能过。

换成 **NPMI**（把 PMI 除以这个词自身的信息量）之后，值域变成 [-1, 1]，与语料大小无关，阈值定 0.5 就能长期用：

```java
double pw = (double) fg / c.total;
double selfInfo = -Math.log(pw) / Math.log(2);
for (int i = 1; i < g.length(); i++) {
    double fl = Math.max(counts.get(left),  0.5);   // 平滑方向很关键
    double fr = Math.max(counts.get(right), 0.5);
    double pmi = Math.log((double) fg * c.total / (fl * fr)) / Math.log(2);
    best = Math.min(best, pmi / selfInfo);          // 取所有切分里最差的那个
}
```

两个细节值得说：

1. **取 min 而不是平均。** 一个串只要存在任何一种"切开后两半各自很常见、合起来不奇怪"的切法，它就不算词。
2. **平滑要往让新词活下来的方向平滑。** 一开始我写的是"如果某一半从来没单独出现过，那这个候选直接 0 分"。方向恰好反了——两半都不单独出现的串，正是最像新词的那种。改成 0.5 的 epsilon 之后才正常。

## 二、BM25：把"字段数"当成"文档数"，排序会悄悄变坏

第二个坑是我自己写出来的，而且**肉眼看不出来**。

IDF 的分母应该是包含这个词的**文档数**。我有三个字段（标题/正文/标签），每个字段一份倒排，我当时写的是：

```java
// 错得离谱但看起来很有道理
for (int f = 0; f < FIELDS.size(); f++) if (postings[f].containsKey(term)) n++;
return n;                      // 返回 1 或 2
```

于是**所有词的 IDF 都变成 ln(1+(84-1.5)/1.5) 或 ln(1+(84-2.5)/2.5)**——罕见词和常见词几乎一样响，BM25 退化成"谁词频高谁赢"。结果依然是"对的"，只是排序质量肉眼不可见地掉了。

抓出来靠的是一条测试：

```java
@Test
void rareTermDominates() {
    // 三个文档，"疫苗" df=1，"资料" df=2，词频相同
    double byRare = bm25.score(idx, List.of("疫苗")).get(0);
    double byCommon = bm25.score(idx, List.of("资料")).get(1);
    assertTrue(byRare > byCommon);
}
```

修成跨字段去重的真实文档数之后，recall@5 从 0.921 变成 0.934。

**0.013 看起来不多，但这条测试值 0.013。** 检索项目最容易烂掉的地方就在这：改完一版，你没法说清它变好了还是变坏了。所以我从第一天就把评测集当交付物——`data/eval/queries.jsonl` 里 38 条查询、手工标注相关文档，每次改排序代码跑一遍 `mini-search eval`，数字进提交说明。

## 三、向量检索：84 篇文档训不出任何东西，于是我给它加了个门槛

原计划里有"本地 bge 小模型"。做到这一步我发现真正的问题不是模型体积，而是**我的演示语料只有 84 篇**。

我用手写的 SGNS（skip-gram + 负采样）在同一份语料上训了词向量，然后老老实实跑评测：

```
| mode    | recall@5 | nDCG@5 |
| bm25    | 0.934    | 0.912  |
| vector  | 0.026    | 0.011  |   ← 约等于随机
| hybrid  | 0.671    | 0.434  |   ← 被这一路拖垮
```

原因不神秘：SGNS 要几百万 token 的上下文才能收敛，我这份语料一共 7 千 token。7 千 token 训不出语义，只能训出噪声——而 **hybrid 会诚实地把噪声一起融进去**，于是混合比单路还差。

同一份代码在 5 万篇文档（约 700 万 token）上就是另一回事：30000 词表、5100 万次梯度更新、140 秒训练完、HNSW 建图 156 秒、hybrid p50 21.6 ms。

所以我的处理是：**给向量层加数据量门槛。**

```java
public long minTokensForEmbeddings = 400_000;

// 启动时：
[mini-search] vector layer skipped: 7,104 corpus tokens < 400,000 needed for a
             useful embedding; mode=semantic and mode=bm25 remain available
```

不够就不出场，而不是装模作样地提供一路随机召回。想要强行打开有 `--force-vectors`，但我会在 README 里告诉你那样做的实测后果。

小语料下的语义靠另一个更老的东西顶上：**分布式同源词典**（SMART 那一代的共现余弦，不用训练）。对每个词统计"出现在同一篇文档里的其他词"，用二值文档向量的余弦排序，查询时把 top-k 邻居拼进去再跑 BM25。它能真的把"纸币"接到"纸质货币"，而且 84 篇文档就有 1220 个词条。

## 四、HNSW：手写最难的部分不是图，是"你怎么知道它没写错"

分层可导航小世界图我全手写了：节点层级按几何分布抽样、顶层贪心下降、底层用 `efConstruction` 宽度的候选队列扩展、双向连边、超容量按距离裁剪。

图本身几百行。**真正让它可用的是那条测试**：

```java
// 1500 条随机向量，与暴力 KNN 逐查询比对
assertTrue(recall >= 0.95, "HNSW recall@10 = " + recall);
// 并且：ef 调小，召回绝不允许变好
assertTrue(recallAtEf10 <= recallAtEf64);
```

第二条看起来像废话，其实它专门用来抓"看起来更快更准"的 bug——如果你把结果排序方向写反、或者候选队列上限写错，很容易出现"队列越小效果越好"的荒谬现象。有了这条断言，任何让 ef 变成假旋钮的改动都会在 CI 上红。

裁剪我用的是"按距离取最近 M 个"，比论文的相对近邻启发式简单，在聚簇数据上会亏一点召回。**这个亏了多少是被测出来的**，所以它是一个已知的取舍，不是一个隐藏的问题。

## 五、剩下两个诚实的坏消息

1. **有 2 条查询任何词法方法都打不中**："小孩高烧不退是细菌感染吗"（目标是《感冒和流感的区别》）、"为什么海边城市冬天不太冷"（目标是《海洋如何调节气候》）。这是真正的同义词/常识鸿沟，共现词典也接不上，得上预训练嵌入。这两条我写在 README 里，不藏在"效果拔群"后面。
2. **同源词典在合成语料上会退化。** 5 万篇 bench 文档是拿同一批句子重组出来的，几乎所有词都互相共现，余弦彻底失去区分度（那次跑只挖出 6 个词条）。真实文档天然是稀疏的——真实抓取和真实笔记没问题，但这条也得说。

## 六、怎么读这份代码

按这个顺序读，每层都不超过 700 行：

```
analyzer/  683  归一化 → 双向最大匹配 → 统计新词挖掘
index/     479  term → (docs + positions)，变长编码，删除位图
ranking/    82  BM25
semantic/  145  分布式同源词典
vector/    717  SGNS 词向量、暴力 KNN、HNSW
hybrid/     76  RRF
search/    405  查询编排（一条查询的完整路径都在这一个文件里）
```

跑起来：

```bash
git clone https://github.com/JingYu-create520/mini-search
cd mini-search && mvn -B package
java -jar target/mini-search.jar            # http://localhost:9200
java -jar target/mini-search.jar eval       # 上面那张表
java -cp target/classes dev.jingyu.ms.MiniSearch analyze "中文分词与倒排索引"
```

如果只看一个东西，建议看 `data/eval/report.md`：它把每一条查询、每一种模式的命中/未命中都摊平了。检索系统的尊严就在这张表里。
